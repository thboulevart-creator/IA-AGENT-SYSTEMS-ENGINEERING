# V3.3 — SYSTEM CONTRACT AND INVARIANT REGISTER

**Version:** V0.1  
**Status:** ACTIVE / QUALIFICATION BASELINE  
**Scope:** `download_ticks_v3_3.ps1` and its qualification harness  
**Source baseline under qualification:** commit `9a45c9a4056ca281d840b465b7e32ca18e6ba59d`  
**Phase:** V3.3 ARCHITECTURAL QUALIFICATION

> This document is the normative design boundary for the V3.3 qualification work. Patches, harness behavior, failure injection, and recovery tests must prove the properties defined here rather than redefine the acceptance target after implementation.

---

## 1. Purpose

V3.3 is not being qualified merely because it can download a file successfully.

The qualification objective is narrower and stronger:

> **Demonstrate, through falsifiable controlled evidence, that the downloader cannot silently transform an incorrect, incomplete, corrupted, ambiguous, or otherwise insufficiently validated acquisition into a state represented as valid RAW/VALID.**

This contract translates the formal triangulation of:

- Claude's architectural review and methodological observations;
- Grok's adversarial audit of commit `9a45c9a4056ca281d840b465b7e32ca18e6ba59d`;
- the permanent project governance rules;
- the existing qualification methodology;

into explicit properties that implementation and testing must satisfy.

Model agreement is not evidence. The contract is therefore expressed in terms of observable states, failure conditions, and required evidence.

---

## 2. Normative evidence rules

The following permanent governance rules apply without modification:

- observation is not interpretation;
- correction is not validation;
- AI agreement is not evidence;
- no false PASS;
- uncertainty is preserved;
- invariants must be falsifiable;
- qualification is stronger than successful execution;
- common-mode validation failure must be avoided;
- the harness is itself auditable;
- critical rejection properties require failure injection;
- critical qualification claims require an independent oracle/reference where practical;
- BLOCKED remains BLOCKED;
- historical success is not current qualification evidence;
- the expensive real-data gate follows synthetic/adversarial qualification.

These rules are inherited from `docs/ARCHITECTURAL-GOVERNANCE-RULES.md` and are not weakened by this document.

---

## 3. Scope and non-scope

### In scope

1. acquisition result handling;
2. RAW creation and persistence;
3. VALID qualification state;
4. SKIP behavior;
5. restart/recovery semantics;
6. integrity identity (including SHA-256 and size where contractually used);
7. structural tick-file validation;
8. timestamp bounds and monotonicity;
9. volume validity;
10. single-CSV / ambiguity rejection;
11. download-failure handling;
12. post-copy validation and corruption handling;
13. manifest evidence and state transitions;
14. harness/oracle independence;
15. controlled failure injection and recovery evidence.

### Not sufficient by itself to establish

- correctness of the external NAS100 data source;
- semantic identity of every downloaded instrument beyond the contractually defined checks;
- completeness of a ten-year historical dataset;
- absence of every possible Dukascopy/provider-side defect;
- universal correctness of future downloader versions;
- trading-strategy validity.

These claims require additional evidence and must not be inferred from V3.3 qualification.

## 4. Canonical state vocabulary

The following terms are normative for this qualification.

### ACQUIRED

A transfer produced an artifact. Acquisition alone says nothing about validity.

### INTEGRITY VALID

The artifact satisfies the declared byte/file integrity checks required by the current contract.

### STRUCTURALLY VALID

The artifact satisfies the required file/schema constraints.

### TEMPORALLY VALID

The tick timestamps satisfy the declared date/window and ordering constraints.

### SEMANTICALLY VALID

The artifact satisfies the semantic properties explicitly covered by the contract. This label must not be used for properties that are not actually checked.

### COMPLETE

The artifact satisfies a separately defined completeness criterion. A readable file is not automatically complete.

### VALID

The implementation has produced a manifest/state representation asserting that all mandatory acceptance conditions for the V3.3 contract have passed.

### SKIP

The downloader intentionally does not reacquire because an existing artifact is proven equivalent to the previously qualified artifact under the current contract.

Existence alone is insufficient for SKIP.

### FAIL

A tested acceptance property was violated or an invalid state was detected.

### BLOCKED

A required test or qualification action cannot execute or cannot produce sufficient evidence because a prerequisite is unavailable or the evidence is insufficient.

BLOCKED is not PASS.

### QUALIFIED

A versioned baseline has passed the complete required qualification evidence set. VALID for one file/date is not equivalent to global QUALIFIED status.

## 5. System Contract

### SC-V33-001 — No silent promotion to VALID

**Criticality:** CRITICAL  
**Status:** TO-PROVE

An artifact may not reach `VALID` if any mandatory acceptance condition is false, unknown, ambiguous, or unverified.

#### Acceptance property

```text
VALID => ALL mandatory acceptance predicates = TRUE
```

#### Failure condition

Any injected invalid acquisition reaches VALID without an explicit contradictory failure state.

#### Required evidence

Controlled failure injection covering each critical rejection class.

---

### SC-V33-002 — VALID implies integrity identity

**Criticality:** CRITICAL  
**Status:** TO-PROVE

A VALID artifact must have a reproducible integrity identity sufficient to distinguish it from an altered artifact under the contract.

At minimum, where SHA-256 is the declared identity, the stored proof must correspond to the bytes actually represented by the qualified RAW.

#### Failure condition

A changed RAW is accepted as the previously qualified artifact without detecting the identity mismatch.

#### Required evidence

Post-VALID mutation tests, including same-size mutation and content replacement.

---

### SC-V33-003 — Post-copy failure cannot poison deterministic restart

**Criticality:** CRITICAL  
**Status:** FAIL — current baseline

A failure after RAW creation/copy but before successful qualification must not leave an ambiguous RAW state that causes subsequent correct recovery to become permanently or spuriously BLOCKED.

#### Current defect

Grok identified C-01: post-copy integrity failure can leave RAW on disk while no corresponding VALID exists, after which a retry encounters the existing RAW and becomes BLOCKED.

#### Acceptance property

```text
post-copy failure
→ explicit failure/quarantine/cleanup state
→ deterministic retry path
```

#### Failure condition

```text
post-copy failure
→ orphan RAW
→ next run
→ permanent BLOCKED without a valid recovery reason
```

#### Required evidence

Injected post-copy corruption/integrity failure followed by an independent fresh retry.

---

### SC-V33-004 — SKIP requires current integrity verification

**Criticality:** CRITICAL  
**Status:** FAIL — current baseline

SKIP may occur only when the existing RAW is demonstrated to correspond to the recorded VALID evidence.

#### Current defect

Grok identified C-02: the existing SKIP path checks RAW existence but does not recompute and compare its current SHA/size against the recorded VALID proof.

#### Acceptance property

```text
SKIP => current RAW identity == recorded VALID identity
```

#### Failure condition

A previously VALID RAW is modified and the next invocation returns SKIP without detecting the mutation.

#### Required evidence

1. byte mutation with same size;
2. replacement with different size;
3. deletion/recreation where applicable;
4. repeated SKIP after an unchanged valid artifact.

---

### SC-V33-005 — Invalid acquisition is never equivalent to success

**Criticality:** CRITICAL  
**Status:** TO-PROVE

Download failure, malformed content, ambiguous content, validation failure, and integrity failure must remain distinguishable from successful qualification.

#### Failure condition

Any invalid acquisition produces a VALID manifest record or equivalent success state.

#### Required evidence

Failure injection for network/download failure, malformed data, multiple CSVs, timestamp violations, invalid volume values, integrity mismatch, and post-copy corruption.

---

### SC-V33-006 — Validation layers remain distinct

**Criticality:** HIGH  
**Status:** TO-PROVE

The implementation must not collapse these distinct propositions:

```text
TRANSFERRED
→ INTEGRITY VALID
→ STRUCTURALLY VALID
→ SEMANTICALLY VALID
→ TEMPORALLY VALID
→ COMPLETE
→ QUALIFIED
```

Passing one layer does not imply passing all later layers.

#### Failure condition

An upstream technical success is used as evidence for a downstream property that was not checked.

---

### SC-V33-007 — Runtime claims require runtime evidence

**Criticality:** CRITICAL  
**Status:** BLOCKED until executable evidence exists

Any claim about actual runtime behavior must be supported by execution against the current baseline and attributable artifacts.

Static inspection may establish implementation facts but cannot by itself establish runtime qualification.

#### Failure condition

A runtime property is marked PASS solely because the code appears to implement it or because an historical run succeeded.

---

### SC-V33-008 — Critical rejection properties require adversarial failure injection

**Criticality:** CRITICAL  
**Status:** TO-PROVE

For every critical property whose purpose is to reject invalid state, the qualification harness must deliberately inject the corresponding invalid condition.

#### Required minimum attack classes

- malformed tick content;
- missing artifact;
- out-of-window timestamp;
- non-monotonic timestamps;
- invalid volume values;
- multiple CSV ambiguity;
- download failure;
- post-copy corruption;
- post-VALID RAW mutation;
- stale/inconsistent manifest state.

---

### SC-V33-009 — Qualification oracle must not reproduce the implementation's critical assumption

**Criticality:** CRITICAL  
**Status:** TO-PROVE

Where practical, the oracle must derive expected outcomes through an independent representation, calculation, or direct filesystem observation.

#### Failure condition

The downloader and oracle share an unverified critical assumption such that both can agree on a wrong result.

#### Required evidence

Oracle review plus mutation/negative tests designed to expose common-mode failure.

---

### SC-V33-010 — Harness is coordinator, not truth authority

**Criticality:** HIGH  
**Status:** TO-PROVE

The harness may orchestrate setup, mutation, execution, observation, and recording, but objective truth must be derived from the designated oracle/environment evidence rather than from harness assertions alone.

Canonical roles:

```text
ENVIRONMENT = external state
SYSTEM      = downloader under test
OBSERVER    = observes external state
ORACLE      = determines tested property
HARNESS     = coordinates and records
```

---

### SC-V33-011 — Manifest evidence must preserve state history sufficiently for qualification

**Criticality:** HIGH  
**Status:** TO-PROVE

Manifest records must support reconstruction of the relevant acquisition/validation decision without silently replacing failure evidence with later success.

Concurrent writers, append semantics, duplicate VALID records, and ordering behavior require explicit qualification treatment.

#### Failure condition

Manifest state can be interleaved, overwritten, or interpreted in a way that falsely establishes qualification.

---

### SC-V33-012 — Restart must be deterministic from observable state

**Criticality:** CRITICAL  
**Status:** TO-PROVE

Given the same filesystem, manifest, configuration, and external acquisition response, a retry must produce the same state transition, except where nondeterminism is explicitly part of the contract.

#### Failure condition

The same observable starting state produces an unexplained different qualification outcome, or recovery depends on hidden prior process knowledge.

---

### SC-V33-013 — Instrument/date scope must not be silently inferred beyond the contract

**Criticality:** HIGH  
**Status:** TO-PROVE / scope-limited

Validation may rely on provider behavior only where that reliance is explicit. A file passing generic schema/timestamp checks must not be represented as having stronger semantic identity than the contract actually verifies.

This preserves Grok's M-02 exposure without over-promoting it into an unsupported universal requirement.

---

### SC-V33-014 — Zero-volume policy must be explicit

**Criticality:** MEDIUM  
**Status:** TO-PROVE

The acceptance policy for zero tick volume must be explicitly declared and tested. The current code's acceptance of zero is not automatically a defect merely because a comment suggests zero volume is not expected for Nasdaq.

This is intentionally a contract question rather than an assumed correction.

## 8. Patch derivation rule

No patch is accepted merely because it addresses a finding by name.

Each patch must map to:

```text
DEFECT / RISK
    ↓
SYSTEM CONTRACT PROPERTY
    ↓
INVARIANT
    ↓
FAILURE MODE
    ↓
PATCH BEHAVIOR
    ↓
REGRESSION TEST
    ↓
ADVERSARIAL TEST
    ↓
RECOVERY TEST where applicable
```

A patch that makes a test green without establishing the underlying invariant is insufficient.

In particular:

- C-01 must be corrected through a defined post-copy failure-state policy;
- C-02 must be corrected through current integrity verification before SKIP;
- neither correction alone constitutes qualification.

---

## 9. Harness derivation rule

The harness must be designed from the invariants, not from the implementation's current control flow.

For critical properties it must be possible to ask:

> **What invalid state did we deliberately create, what should have happened, what actually happened, and which independently observable evidence proves the verdict?**

The harness must therefore preserve:

```text
REQUEST
→ EXECUTION
→ EXTERNAL STATE
→ OBSERVATION
→ VALIDATION
→ VERDICT
```

and must not collapse these layers into a single runner status.

## 11. Non-goals / anti-overclaim rules

This contract must not be interpreted as proof that:

- Dukascopy data is inherently correct;
- a valid ZIP is necessarily valid NAS100 data;
- a SHA proves semantic correctness;
- a readable CSV proves completeness;
- one successful ten-year acquisition proves future reproducibility;
- an AI reviewer agreement proves correctness;
- a green unit-test suite proves qualification.

Those would violate the project's evidence hierarchy.
