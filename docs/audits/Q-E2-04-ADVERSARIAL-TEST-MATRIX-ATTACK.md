# Q-E2-04 — Adversarial Test-Matrix Attack

**Verdict:** PASS — conceptual matrix survives attack after mandatory strengthening below.

**Scope:** attack the E2 falsification matrix itself before changing the harness.

## 1. Attack objective

The question is not whether the matrix contains the right threats, but whether a misleading implementation could satisfy the matrix while still failing to demonstrate observation-induced runtime adaptation.

A matrix is insufficient if its own evidence can be produced by the mechanism under test, by shared instrumentation, by a pre-programmed branch, or by a comparison that does not establish the first causal divergence.

## 2. Adversarial attacks

### A01 — Self-authenticating mutation

**Attack:** the harness records `external_mutation` and treats that event as proof that the workspace changed.

**Failure mode:** a recorded mutation is not equivalent to a verified state change.

**Countermeasure:** after mutation, require an independent observer to show a changed external artifact state, and require `CHECK_ARTIFACT`/oracle evidence that the objective was actually invalidated.

**Disposition:** matrix strengthened; mutation metadata is evidence of the intervention, not proof of its effect.

### A02 — Self-authenticating observation

**Attack:** the observation event is accepted merely because the runner emitted it.

**Failure mode:** instrumentation could report `FAIL` without the workspace actually being invalid.

**Countermeasure:** compare observation data against independently captured workspace state and the oracle/check result. A trace-only observation can never establish the causal fact.

**Disposition:** matrix strengthened.

### A03 — Pre-scripted repair disguised as adaptation

**Attack:** a controller always executes `CHECK -> REPAIR -> CHECK`, regardless of observation.

**Failure mode:** the perturbed case succeeds, but the action is not observation-dependent.

**Countermeasure:** identify the first divergent decision between paired normal and perturbed runs and require the divergence to occur only after the divergent observation. The normal branch must not execute the repair action.

**Disposition:** already covered by F01/F06/F21; strengthened to require first-divergence evidence, not merely different final traces.

### A04 — Condition leakage through experiment plumbing

**Attack:** the controller indirectly learns `perturbed=True`, experiment ID, fault metadata, mutation type, or run configuration.

**Failure mode:** action divergence is caused by hidden condition metadata rather than the observed external state.

**Countermeasure:** provider interface receives only objective, observation, and prior history. Audit the provider implementation and invocation arguments; mutation metadata never enters provider inputs.

**Disposition:** F02/F15 retained as hard blockers.

### A05 — Observation contains the answer rather than reality

**Attack:** observer supplies an explicit `"repair_required": true` flag generated by the harness.

**Failure mode:** controller is reacting to an injected label rather than external state.

**Countermeasure:** observation must expose raw/derived external state available from the workspace and the tool result, while the repair decision is independently reconstructed from the observed mismatch. No perturbation label or mutation metadata is provider-visible.

**Disposition:** F09/F15 strengthened.

### A06 — Tool result smuggles mutation information

**Attack:** the mutation hook changes the tool result or inserts a failure status, so the controller is reacting to a synthetic tool claim rather than the changed workspace.

**Failure mode:** no external-state causality.

**Countermeasure:** mutation occurs after tool execution; observer reads the workspace independently; the post-mutation `CHECK_ARTIFACT` is the source of the FAIL observation used at the causal decision point.

**Disposition:** F08/F09/F21 retained as hard blockers.

### A07 — Hash collision / weak state evidence

**Attack:** state equality is inferred from weak or ambiguous summaries.

**Failure mode:** apparent state difference does not establish an actual artifact change.

**Countermeasure:** use SHA-256 artifact hashes plus final independent oracle verification. The controlled corruption must change bytes deterministically.

**Disposition:** acceptable for this deterministic local file experiment; matrix requires actual byte-level mismatch, not merely a metadata difference.

### A08 — Initial-state mismatch hidden by fresh workspaces

**Attack:** normal and perturbed runs use different source content or different initial workspace state.

**Failure mode:** action divergence may be caused before perturbation.

**Countermeasure:** pair by exact scenario ID, seed, objective version, initial workspace snapshot/hash, tool/fault configuration, authorized actions, and controller configuration. The perturbation is the only intended post-write difference.

**Disposition:** F03/F12/F13/F14 retained as pair-comparability gates.

### A09 — Different action budget creates the result

**Attack:** perturbed S2 gets more opportunities to recover than normal S2, making the apparent advantage a budget artifact.

**Failure mode:** causal claim confounded by unequal compute/action budget.

**Countermeasure:** identical configured action budget and execution constraints. The audit may allow a different number of actions after the first causal divergence, but not a different maximum budget.

**Disposition:** F05/F06 retained.

### A10 — First divergence is hidden by lossy trace matching

**Attack:** audit compares only final action sequences or final outcomes.

**Failure mode:** an earlier unexplained divergence could cause everything that follows.

**Countermeasure:** pair traces and locate the earliest action difference. Require: common prefix, divergent observation, then divergent decision/action. Any earlier unexplained divergence is FAIL; an inability to locate it is BLOCKED.

**Disposition:** F06/F10/F21 strengthened.

### A11 — Oracle shares the implementation under test

**Attack:** both WRITE and CHECK rely on the same transformation function, allowing a shared bug to make corruption/repair appear valid.

**Failure mode:** internal consistency is mistaken for independent correctness.

**Countermeasure:** final oracle must independently derive expected content; current repository has an architectural exposure because `tools.py` imports `canonical_transform` from `oracle.py`. This is not an E2 FAIL by itself, but it limits independence. E2 must not claim full transformation independence until this exposure is separately resolved.

**Disposition:** explicit scope restriction; final E2 verdict cannot silently promote this exposure to PASS.

### A12 — Scripted controller proves more than it can

**Attack:** deterministic S2 passes the experiment and the result is generalized to LLM agent behavior.

**Failure mode:** experiment establishes only a closed-loop controller property.

**Countermeasure:** final claim is scoped to the tested S2 implementation. LLM generalization remains unproven unless an actual LLM variant is executed under the same controls.

**Disposition:** F22 is a hard scope gate.

### A13 — False FAIL / false PASS at the check boundary

**Attack:** CHECK reports FAIL while the artifact is valid, or PASS while it is invalid.

**Failure mode:** the causal branch is driven by an incorrect verifier.

**Countermeasure:** cross-check CHECK result against the independent final oracle and externally observed artifact state. Any contradiction is FAIL; inability to establish agreement is BLOCKED.

**Disposition:** F17/F18 retained as hard blockers.

### A14 — Mutation is deterministic but ineffective

**Attack:** corruption changes a byte that does not alter the objective, or the chosen byte happens already to produce the expected result.

**Failure mode:** the perturbed and normal cases are not causally different.

**Countermeasure:** prove oracle PASS immediately before mutation and oracle FAIL / byte inequality immediately after mutation, before interpreting any adaptive behavior.

**Disposition:** F07 made mandatory.

### A15 — Repair succeeds but does not address the observed defect

**Attack:** REPAIR always rewrites the correct artifact, but the audit ignores whether the action was selected because of the mismatch.

**Failure mode:** successful repair is mistaken for adaptation.

**Countermeasure:** adaptation requires both first-divergent action evidence and subsequent oracle PASS. Resolution alone is insufficient.

**Disposition:** F11/F16 strengthened.

## 3. Mandatory matrix amendments

The original matrix is therefore sufficient only after making these gates explicit:

1. **Intervention-effect gate:** prove the mutation changed external state and invalidated O1.
2. **Observation-independence gate:** observation evidence must be reconstructable from external state; mutation labels cannot substitute for reality.
3. **First-divergence gate:** compare paired traces at the earliest action divergence, not only final sequences.
4. **Provider-input gate:** capture/audit the exact provider-visible observation and history; no experiment metadata may cross the boundary.
5. **Pair-equivalence gate:** exact initial-state and configuration equivalence is required.
6. **Resolution gate:** final independent oracle PASS is required after the divergent action.
7. **Controller-scope gate:** claims are limited to the tested controller class.
8. **Oracle-exposure disclosure:** shared transformation code remains an architectural exposure and must not be described as fully independent verification.

## 4. Q-E2-04 verdict

**PASS — conceptual matrix complete after attack.**

The matrix is not accepted merely because it lists common confounders. It now explicitly attacks the possibility that the evidence produced by each control is itself misleading.

No harness modification is justified by this step alone. The next step is to convert these strengthened gates into executable requirements and then implement the smallest formal paired E2 harness on the isolated branch.
