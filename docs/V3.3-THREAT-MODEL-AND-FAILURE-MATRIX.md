**Version:** V0.1  
**Status:** ACTIVE / QUALIFICATION DESIGN  
**Scope:** `download_ticks_v3_3.ps1` qualification  
**Contract baseline:** `docs/V3.3-SYSTEM-CONTRACT-AND-INVARIANT-REGISTER.md` V0.1

> This document derives adversarial threats and executable failure scenarios from the V3.3 System Contract. It does not modify the acceptance criteria to fit the implementation.

---

## 1. Objective

The threat model answers one question:

> **How could an incorrect, incomplete, corrupted, ambiguous, or stale acquisition cross the V3.3 qualification boundary and be represented as valid?**

The failure matrix converts each relevant threat into a controlled experiment with:

- precondition;
- injected fault;
- expected state;
- forbidden state;
- independent oracle;
- recovery expectation;
- evidence artifact;
- verdict rule.

A scenario without an executable oracle is not a PASS candidate. It is TO-PROVE or BLOCKED according to the missing prerequisite.

---

## 2. Threat model boundaries

### Assets to protect

1. integrity of the downloaded RAW artifact;
2. correctness of the VALID qualification claim;
3. determinism of restart/recovery;
4. integrity and interpretability of manifest evidence;
5. separation between system behavior and qualification verdict;
6. trustworthiness of the eventual ten-year acquisition dataset.

### Adversaries / fault sources

The model does not assume a malicious human only. The relevant adversary is any condition capable of producing an invalid state, including:

- network/download failure;
- truncated or malformed archive;
- malformed tick content;
- ambiguous archive contents;
- timestamp corruption;
- non-monotonic ticks;
- invalid volume values;
- post-copy corruption;
- post-VALID mutation;
- stale or inconsistent manifest state;
- concurrent manifest writers;
- partial cleanup;
- process interruption;
- environment incompatibility;
- provider-side unexpected content;
- test-harness/oracle common-mode error.

### Trust boundaries

```text
EXTERNAL PROVIDER / NETWORK
          ↓
DOWNLOAD MECHANISM
          ↓
TEMP / EXTRACTION STATE
          ↓
VALIDATION
          ↓
RAW ARTIFACT
          ↓
MANIFEST / PROOF
          ↓
SKIP / RECOVERY
          ↓
QUALIFICATION HARNESS
          ↓
FINAL VERDICT
```

Every arrow is a potential trust-boundary crossing. Success at an earlier boundary must not be treated as proof that later boundaries are safe.

## 4. Critical failure matrix

### FM-001 — Download failure cannot become VALID

**Maps to:** SC-V33-001, SC-V33-005, SC-V33-008  
**Threat:** T1  
**Criticality:** CRITICAL

**Precondition:** clean date-specific acquisition state.

**Injection:** force the acquisition mechanism to fail (non-zero exit, unavailable source, simulated failed transfer, or controlled mock at the download boundary).

**Expected:** explicit failure/non-success state; no VALID record; no claim that the requested artifact was qualified.

**Forbidden:** VALID manifest record, success exit status representing qualification, or a later SKIP based on nonexistent valid proof.

**Oracle:** filesystem + manifest parsed independently of downloader return value.

**Recovery:** a later successful acquisition may proceed from a clean recoverable state.

**Evidence:** command exit code, stdout/stderr capture, filesystem tree, manifest before/after, SHA where applicable.

**Verdict:** PASS only if all forbidden states are absent and expected state is independently observed.

---

### FM-002 — Malformed tick content is rejected

**Maps to:** SC-V33-001, SC-V33-005, SC-V33-008  
**Threat:** T2  
**Criticality:** CRITICAL

**Injection:** replace/extract a fixture containing invalid tick schema/content while keeping the surrounding acquisition envelope otherwise plausible.

**Expected:** validation failure; no VALID.

**Forbidden:** malformed fixture represented as VALID.

**Oracle:** independent fixture parser/schema checks plus filesystem/manifest observation.

**Recovery:** invalid artifact is cleaned/quarantined or otherwise made non-authoritative for retry.

**Evidence:** fixture hash, validator result, manifest, final directory state.

---

### FM-003 — Timestamp outside requested date/window is rejected

**Maps to:** SC-V33-001, SC-V33-005, SC-V33-008  
**Threat:** T3  
**Criticality:** CRITICAL

**Injection:** fixture containing at least one tick outside the declared requested temporal bounds.

**Expected:** rejection; no VALID.

**Forbidden:** acceptance as if all ticks belonged to the requested date.

**Oracle:** independently calculated min/max timestamp from fixture.

**Recovery:** deterministic invalid-state handling.

**Evidence:** fixture timestamps, requested bounds, independently calculated extrema, manifest/state.

---

### FM-004 — Non-monotonic timestamps are rejected

**Maps to:** SC-V33-001, SC-V33-005, SC-V33-008  
**Threat:** T3  
**Criticality:** CRITICAL

**Injection:** construct a fixture with otherwise valid rows but deliberately reverse or duplicate ordering in a way forbidden by the declared contract.

**Expected:** rejection when the contract requires strict ordering.

**Forbidden:** VALID while violating the declared ordering predicate.

**Oracle:** independent adjacent-timestamp ordering check.

**Recovery:** same as malformed-data recovery.

**Evidence:** exact offending rows/positions, independent ordering result, state transition.

> The harness must not silently strengthen the contract from non-decreasing to strictly increasing unless the contract is explicitly updated first.

---

### FM-005 — Invalid volume values are rejected

**Maps to:** SC-V33-001, SC-V33-005, SC-V33-008, SC-V33-014  
**Threat:** T2  
**Criticality:** CRITICAL for NaN/Inf/negative; policy-dependent for zero

**Injection:** fixtures containing NaN/Inf/negative volume and, separately, zero volume.

**Expected:** NaN/Inf/negative rejected; zero follows explicit policy.

**Forbidden:** implicit acceptance/rejection of zero based solely on an informal comment.

**Oracle:** independent numeric predicate.

**Evidence:** fixture values, policy identifier, validator result, manifest/state.

---

### FM-006 — Multiple CSV contents are rejected as ambiguous

**Maps to:** SC-V33-001, SC-V33-005, SC-V33-008  
**Threat:** T4  
**Criticality:** CRITICAL

**Injection:** archive/extraction fixture containing multiple candidate CSV files where exactly one is required by the contract.

**Expected:** explicit ambiguity rejection.

**Forbidden:** arbitrary file selection followed by VALID.

**Oracle:** independent directory enumeration and count.

**Recovery:** ambiguous temporary/extracted state cannot become authoritative RAW.

**Evidence:** archive fixture hash, extracted file listing, selected/rejected state.

---

### FM-007 — Post-copy corruption cannot leave an unrecoverable RAW

**Maps to:** SC-V33-003, SC-V33-012  
**Threat:** T5  
**Criticality:** CRITICAL

**Precondition:** acquisition has produced a candidate RAW and validation is about to complete.

**Injection:** deliberately alter/corrupt the RAW after copy and before successful qualification.

**Expected:** integrity failure is recorded; RAW is removed, quarantined, or otherwise prevented from blocking a correct retry according to the implementation's defined policy.

**Forbidden:** orphan RAW followed by a retry that becomes spuriously/permanently BLOCKED merely because the invalid artifact remains.

**Oracle:** independent SHA-256 calculation and filesystem state inspection.

**Recovery:** fresh retry with valid fixture must be possible and deterministic.

**Evidence:** pre/post hashes, failure state, filesystem tree, retry result, manifest history.

**Current baseline:** FAIL due to C-01.

---

### FM-008 — Post-VALID mutation cannot produce SKIP

**Maps to:** SC-V33-002, SC-V33-004  
**Threat:** T6  
**Criticality:** CRITICAL

**Precondition:** valid artifact and corresponding VALID proof exist.

**Injection:** mutate one byte without changing file size; repeat with different-size replacement.

**Expected:** integrity mismatch detected; SKIP forbidden.

**Forbidden:** SKIP based only on RAW existence.

**Oracle:** independent SHA-256 and size calculation compared with recorded proof.

**Recovery:** explicit integrity failure/reacquisition path.

**Evidence:** original SHA/size, mutated SHA/size, manifest, invocation result.

**Current baseline:** FAIL due to C-02.

---

### FM-009 — Unchanged VALID artifact may SKIP deterministically

**Maps to:** SC-V33-002, SC-V33-004, SC-V33-012  
**Threat:** T6/T9  
**Criticality:** HIGH

**Precondition:** a legitimately VALID artifact exists and remains unchanged.

**Injection:** repeated invocations without changing filesystem/configuration/provider response.

**Expected:** SKIP with unchanged artifact identity and consistent manifest semantics.

**Forbidden:** silent reacquisition, mutation, or contradictory state transitions without an explicit reason.

**Oracle:** pre/post independent hash and size plus filesystem/manifest observation.

**Recovery:** not applicable.

**Evidence:** run-by-run state, hashes, exit codes, manifest deltas.

---

### FM-010 — Stale/inconsistent manifest cannot authorize a false state

**Maps to:** SC-V33-004, SC-V33-011  
**Threat:** T7  
**Criticality:** CRITICAL

**Injection:** create manifest records that claim VALID while the corresponding RAW is missing, changed, or inconsistent with recorded identity.

**Expected:** the downloader refuses to treat the stale proof as sufficient authorization.

**Forbidden:** VALID/SKIP based solely on stale manifest assertions.

**Oracle:** independently compare manifest claims with current filesystem/hash state.

**Evidence:** crafted manifest, RAW state, computed identity, resulting transition.

---

### FM-011 — Concurrent manifest writers cannot silently corrupt qualification evidence

**Maps to:** SC-V33-011  
**Threat:** T8  
**Criticality:** HIGH

**Injection:** run controlled concurrent writers or simulate interleaving append operations.

**Expected:** records remain parseable and attribution/order semantics remain within the declared contract, or concurrency is explicitly rejected/serialized.

**Forbidden:** malformed/interleaved records that can later be interpreted as valid evidence.

**Oracle:** independent CSV/parser plus record-count and field-integrity checks.

**Evidence:** concurrent run logs, resulting manifest bytes, parser result, record attribution.

**Current baseline:** architectural exposure identified by Grok; runtime qualification pending.

---

### FM-012 — Restart is independent of hidden process state

**Maps to:** SC-V33-003, SC-V33-012  
**Threat:** T9  
**Criticality:** CRITICAL

**Injection:** terminate the process at defined state boundaries, then start a fresh process with the same observable filesystem/manifest/configuration.

**Expected:** deterministic recovery according to the state contract.

**Forbidden:** recovery requiring memory of the previous process or producing unexplained state transitions.

**Oracle:** independently captured filesystem/manifest snapshot before and after restart.

**Evidence:** kill point, snapshot, new process result, final snapshot.

---

### FM-013 — Harness/oracle common-mode failure is exposed

**Maps to:** SC-V33-009, SC-V33-010  
**Threat:** T10  
**Criticality:** CRITICAL

**Injection:** construct fixtures that distinguish an implementation assumption from an independent reference result.

**Expected:** oracle can disagree with the implementation and the harness reports the discrepancy rather than normalizing it.

**Forbidden:** harness derives expected output by calling/reproducing the same validation logic under test.

**Oracle:** independent parser/calculator/reference fixture or authoritative external specification where applicable.

**Evidence:** oracle source, fixture, expected result, system result, disagreement handling.

---

### FM-014 — Static evidence cannot close runtime gates

**Maps to:** SC-V33-007  
**Threat:** T11  
**Criticality:** CRITICAL

**Injection:** none; this is an evidence-integrity control.

**Expected:** runtime-only claims remain BLOCKED until executable evidence exists.

**Forbidden:** static code inspection or historical success converted into runtime PASS.

**Oracle:** evidence ledger showing executable run attributable to the current baseline.

---

### FM-015 — Semantic scope is not overclaimed

**Maps to:** SC-V33-006, SC-V33-013  
**Threat:** T12  
**Criticality:** HIGH

**Injection:** provide structurally valid fixture whose semantic identity is deliberately outside what generic validation can distinguish.

**Expected:** system/harness reports only the properties actually checked.

**Forbidden:** claiming instrument identity/completeness merely because schema and timestamps pass.

**Oracle:** contract-to-check mapping.

**Evidence:** exact predicates executed and explicit non-claims.

---

### FM-016 — Cleanup failure cannot silently contaminate next run

**Maps to:** SC-V33-003, SC-V33-012  
**Threat:** T13  
**Criticality:** HIGH

**Injection:** force temp-file/directory cleanup failure.

**Expected:** residual state is either safely isolated, explicitly detected, or otherwise cannot be mistaken for authoritative RAW/VALID state.

**Forbidden:** stale temp content silently selected on a later run.

**Oracle:** filesystem enumeration independent of cleanup command result.

**Evidence:** residual paths, subsequent invocation, state transition.

---

### FM-017 — Runtime environment incompatibility remains visible

**Maps to:** SC-V33-007  
**Threat:** T14  
**Criticality:** HIGH

**Injection:** execute under a documented unsupported or altered PowerShell/environment condition.

**Expected:** incompatibility is observable and qualification is BLOCKED/FAIL as appropriate.

**Forbidden:** environment-specific failure represented as qualified behavior.

**Oracle:** captured environment fingerprint and exit/result state.

## 6. Required harness capabilities derived from this matrix

The future qualification harness must be able to:

1. create isolated per-test workspaces;
2. generate deterministic valid and invalid fixtures;
3. control the acquisition boundary without relying on live Dukascopy for every negative test;
4. mutate files at precise lifecycle points;
5. terminate/restart the downloader at defined boundaries;
6. independently compute SHA-256 and file size;
7. independently enumerate filesystem state;
8. independently parse/validate manifest records;
9. compare expected and observed state transitions;
10. preserve stdout/stderr and process exit codes;
11. capture environment fingerprints;
12. produce immutable evidence artifacts for each scenario;
13. distinguish FAIL from BLOCKED;
14. refuse to convert missing evidence into PASS.

---

## 7. Oracle requirements

For every CRITICAL scenario the harness specification must identify an oracle before implementation.

Preferred hierarchy:

1. direct filesystem fact;
2. independently implemented calculation;
3. independently parsed fixture;
4. authoritative provider/documentation constraint;
5. implementation-derived expectation only as a last resort, explicitly marked weak.

The oracle must not call the same function under test merely to decide whether that function succeeded.

If no independent oracle can be constructed, the scenario remains explicitly limited and cannot support a stronger qualification claim than its evidence permits.

---

## 8. Recovery model

Recovery must be evaluated as a state transition, not as a single exit code.

Canonical model:

```text
CLEAN
  ↓
ACQUISITION
  ↓
CANDIDATE RAW
  ↓
VALIDATION
  ├── SUCCESS → VALID
  └── FAILURE → SAFE FAILURE STATE
                       ↓
                    RETRY
                       ↓
                 DETERMINISTIC RESULT
```

A failure is unsafe if it leaves an artifact that a subsequent invocation interprets as an authoritative prior success or as an unexplained permanent blocker.

---

## 9. Verdict rules

### PASS

Only when:

- the scenario executed on the current baseline;
- the injected fault was confirmed;
- the expected behavior was independently observed;
- forbidden behavior was absent;
- required evidence artifacts are attributable and reproducible;
- the oracle is adequate for the claim.

### FAIL

When the executable test demonstrates a contract violation.

### BLOCKED

When execution cannot occur or evidence cannot establish the claim because of a missing prerequisite, unavailable environment, unavailable dependency, or insufficient runtime access.

### TO-PROVE

Used for a defined property whose executable qualification has not yet been performed, where no current demonstrated violation is established.

### UNKNOWN

Used only when the property itself or its evidence interpretation remains materially unresolved.
