## 1. Purpose

This document freezes the implementation and experimental specification required before runtime qualification of V3.3.

It does **not** redefine acceptance criteria. The System Contract and Invariant Register remain authoritative. The Threat Model and Failure Matrix define the adversarial scenarios. This document translates those requirements into:

1. minimal implementation corrections;
2. regression tests;
3. controlled failure injection;
4. recovery tests;
5. independent qualification oracles;
6. reproducible evidence artifacts.

The central qualification question remains:

> Can an incorrect, incomplete, corrupted, ambiguous, stale, or otherwise insufficiently validated acquisition silently cross the V3.3 boundary and be represented as `VALID` or safely reusable as `SKIP`?

The answer must be established by executable evidence, not by code inspection or AI agreement.

### V0.2 adversarial hardening

V0.1 was rejected by counter-expertise because several requirements were declarative but not sufficiently operationalized. V0.2 therefore adds explicit controls for:

- orphan RAW recovery after crash/kill during failure cleanup;
- the concurrency/mutation model of the SKIP path;
- raw-fixture delivery without validation by the acquisition adapter;
- independent proof that a fault injection actually occurred;
- mandatory common-mode/oracle independence checks;
- machine-checkable evidence completeness;
- explicit qualification blockers;
- manifest tampering and trust-boundary handling.

These additions do not weaken the acceptance target.

---

## 2. Non-negotiable constraints

- No patch is considered validation.
- No successful test is qualification by itself.
- Runtime claims remain `BLOCKED` until executed on the current qualified baseline.
- A failure-injection test must actually introduce the targeted fault; merely exercising an error path is insufficient.
- Critical integrity checks must have an oracle independent of the implementation's critical calculation.
- The harness is a coordinator and evidence collector, not the source of truth.
- Missing, null, unverifiable, or contradictory mandatory evidence cannot produce `PASS`.
- The acceptance target must not be weakened to accommodate the implementation.
- Each patch must have a regression test demonstrating the intended corrected behavior and a failure-injection test demonstrating resistance to the corresponding adversarial condition.
- Recovery must be tested from observable filesystem/manifest state after process termination or failure; hidden in-memory state cannot be used as evidence.
- A raw artifact existing without a corresponding valid proof is **never** sufficient authorization for `SKIP` or qualification.
- A manifest record is evidence, not an independently trusted root of truth; its integrity and consistency must be checked within the qualification boundary.
- Where external mutation/concurrency is outside the supported operating model, that boundary must be explicitly declared and tested as such; it must not remain implicit.

## 3. Patch map

### P-001 — Post-copy integrity failure cleanup / orphan recovery

**FM-ID:** `FM-007`, `FM-012`, `FM-016`  
**Contract / Invariant:** `SC-V33-003`, `SC-V33-012`, `INV-V33-003`  
**Current defect:** A post-copy validation or integrity failure can leave the copied RAW artifact on disk. A subsequent invocation can then encounter `RAW exists without VALID` and become permanently `BLOCKED`, instead of recovering deterministically.

**Patch requirement:** If any post-copy integrity/validation step fails after the RAW artifact has been created, the artifact must be removed or moved to an explicitly non-authoritative quarantine state. The recovery contract must additionally define startup handling for **any RAW present without a corresponding valid proof**, regardless of why it exists. Such an orphan RAW must never be treated as an acquisition-authoritative artifact.

The implementation must satisfy one of these deterministic policies on every invocation:

1. remove orphan RAW;
2. move orphan RAW to a uniquely identifiable non-authoritative quarantine location;
3. explicitly ignore/quarantine it and reacquire from the provider.

If cleanup/quarantine itself fails, the failure must remain observable and the orphan must still be ineligible for `VALID` and `SKIP`. The next invocation must have a deterministic non-authoritative path rather than an unconditional `RAW exists without VALID` dead-end.

The policy must not depend on an in-memory flag from the previous process.

**Regression test:** Run a normal successful acquisition and confirm the expected RAW/VALID lifecycle. Verify no unintended quarantine/deletion occurs.

**Failure-injection test:** Inject corruption/failure after RAW creation and before successful post-copy validation. Separately inject process termination at the cleanup/quarantine boundary. Confirm the resulting RAW, if any, is non-authoritative.

**Recovery test:** Start a fresh process from the exact observable post-crash filesystem/manifest state. Confirm the failed artifact cannot cause permanent restart blocking and that a clean acquisition can proceed.

**Oracle:** Independent filesystem enumeration plus independently computed SHA-256/size and independent manifest parsing.

**Evidence artifact:** Pre/post directory inventory, exact injection point, proof of process termination where used, independent hash/size report, artifact disposition, manifest before/after, recovery-run report.

### P-002 — Current SHA-256/size verification on SKIP

**FM-ID:** `FM-008`, `FM-009`, `FM-010`  
**Contract / Invariant:** `SC-V33-002`, `SC-V33-004`, `INV-V33-002`, `INV-V33-004`  
**Current defect:** The SKIP path can rely on the existence of the RAW path after locating a prior VALID manifest record, without independently confirming that the current RAW artifact still matches the recorded VALID identity.

**Patch requirement:** A SKIP is authorized only after recomputing the current RAW artifact's integrity identity and comparing it to the identity recorded by the relevant VALID proof. At minimum this includes file size and SHA-256.

The qualification model must explicitly distinguish two cases:

- **Supported concurrency model:** the RAW is protected against concurrent mutation during the authorization window by an explicit lock/ownership mechanism, or an equivalent atomic identity check defined by the implementation contract.
- **Unsupported external mutation/concurrency:** the contract explicitly declares that concurrent mutation is outside the supported model, and qualification must demonstrate that such mutation cannot silently create a `SKIP` under the declared boundary.

A mere first hash followed by an unprotected decision is not sufficient where concurrency is in scope.

A mismatch, disappearance, replacement, or unverifiable identity must prevent `SKIP` and produce an explicit integrity failure/blocking outcome consistent with the contract.

**Regression test:** After a valid acquisition, invoke the downloader again without modifying the artifact. Confirm deterministic SKIP and equality of current independent hash/size with recorded VALID proof.

**Failure-injection test:** After VALID, replace or mutate the RAW artifact. Include both different-size and same-size mutations. If concurrency is in scope, synchronize mutation during the SKIP authorization window and prove that no SKIP is emitted for bytes not covered by the accepted identity.

**Recovery test:** Restore the exact VALID artifact and rerun. Confirm SKIP becomes eligible again only after current integrity identity matches the recorded proof.

**Oracle:** Independently computed SHA-256 and byte size, compared directly with the manifest's recorded proof; no reuse of the downloader's hash helper as sole oracle.

**Evidence artifact:** Original hash/size, mutation description, mutated hash/size, timing/lock evidence where applicable, manifest proof, exit code/status, observed transition, restored-artifact hash/size, recovery result.

### P-003 — Preserve explicit failure observability

**FM-ID:** `FM-001`, `FM-005`, `FM-007`, `FM-010`, `FM-016`, `FM-017`  
**Contract / Invariant:** `SC-V33-005`, `INV-V33-005`  
**Current risk:** Different acquisition, validation, filesystem, cleanup, manifest, or environment failures can otherwise become ambiguous from the outside if only a generic exit result is inspected.

**Patch requirement:** Every failure-injection scenario must leave enough externally observable state to distinguish failure from `VALID` and from an eligible `SKIP`. The patch must not suppress evidence needed by the harness. This is primarily an observability requirement; no new success condition may be introduced.

If cleanup cannot complete, that fact itself is evidence and must not be replaced by a success-looking state.

**Regression test:** Successful and rejected acquisitions produce distinguishable status/manifest/filesystem outcomes.

**Failure-injection test:** Inject download failure, malformed content, post-copy failure, cleanup failure, and manifest inconsistency; confirm none creates a VALID proof.

**Recovery test:** Restart after each failure and confirm the resulting state is deterministic and interpretable.

**Oracle:** Exit code + manifest + independent filesystem state.

**Evidence artifact:** Complete execution transcript and state snapshot per scenario.

---

### P-004 — Make zero-volume policy explicit

**FM-ID:** `FM-005`  
**Contract / Invariant:** `SC-V33-014`  
**Current exposure:** The existing validation permits zero volume while comments/semantic assumptions may imply that executed tick volume should be positive. This is a policy question and must not be silently converted into a stricter rule merely because it seems preferable.

**Patch requirement:** Freeze the accepted zero-volume policy in the qualification contract **before** changing implementation behavior. If zero is permitted, tests must explicitly prove that zero is accepted and document why. If zero is forbidden, add the corresponding rejection rule and adversarial test.

**Regression test:** Execute the chosen policy against a fixture containing zero-volume ticks.

**Failure-injection test:** If zero is forbidden, inject zero-volume ticks into otherwise valid content and verify rejection. If zero is permitted, use zero-volume data as a boundary fixture and verify no accidental rejection.

**Recovery test:** Confirm the policy outcome is deterministic on rerun.

**Oracle:** Contract-approved fixture classification, independently parsed.

**Evidence artifact:** Policy decision, fixture, independent parser result, downloader result, manifest/state outcome.

## 4. Harness architecture

The qualification harness must be an **experiment coordinator**, not a second implementation of the downloader.

### 4.1 Required components

1. **Isolated workspace manager**
   - fresh workspace per scenario;
   - no dependency on previous test state;
   - complete pre/post filesystem inventory.

2. **Fixture factory**
   - deterministic valid tick fixture;
   - malformed fixture;
   - out-of-window timestamp fixture;
   - non-monotonic timestamp fixture;
   - invalid-volume fixture;
   - multi-CSV archive fixture;
   - controlled post-copy corruption target;
   - post-VALID mutation fixture;
   - manifest-tampering fixture.

3. **Acquisition boundary adapter**
   - replaces/intercepts the provider acquisition boundary only where necessary for deterministic tests;
   - must deliver the fixture/archive as **raw test input** and must not classify, filter, normalize, validate, or reject it according to downloader acceptance rules;
   - records exactly which raw bytes/archive were supplied;
   - adapter success means only that the requested fixture bytes were supplied, not that the fixture is valid.

4. **Fault injector**
   - explicit named injection points;
   - deterministic activation;
   - injection confirmation must be independently observable;
   - no silent best-effort fault injection;
   - an injector self-reported flag is never sufficient proof by itself.

5. **Independent observer**
   - filesystem enumeration;
   - independent SHA-256/size;
   - independent archive enumeration/parsing;
   - independent manifest parsing;
   - process exit code;
   - stdout/stderr capture;
   - process lifecycle evidence where crash/restart is tested.

6. **Scenario oracle**
   - computes expected state from contract-defined fixture properties and direct external facts;
   - does not call downloader validation functions as its authority;
   - must have a documented assumption set distinct from implementation helpers;
   - must participate in a deliberate disagreement/self-audit test before qualification PASS.

7. **Evidence recorder**
   - immutable per-scenario evidence directory;
   - scenario ID;
   - baseline commit;
   - environment fingerprint;
   - fixture fingerprint;
   - injection confirmation;
   - observed state;
   - oracle result;
   - verdict;
   - completeness validation result.

8. **Verdict engine**
   - PASS only when the scenario's exact mandatory evidence set is complete, non-null, independently attributable, internally consistent, and agrees with the contract;
   - FAIL when executable evidence demonstrates a contract violation;
   - BLOCKED when required execution/evidence cannot be obtained;
   - never upgrades BLOCKED/UNKNOWN to PASS through inference;
   - rejects PASS if any mandatory evidence field is absent, null, contradictory, unverifiable, or produced only by the component whose claim it is intended to prove.

### 4.2 Adapter independence control

The acquisition adapter must be treated as a transport fixture provider, not a semantic validator.

For every adversarial fixture, the harness must preserve:

```text
RAW FIXTURE BYTES
    ↓
ACQUISITION ADAPTER
    ↓
SYSTEM UNDER TEST
    ↓
INDEPENDENT OBSERVER
    ↓
INDEPENDENT ORACLE
```

The adapter must not transform an invalid fixture into a valid one or reject it before the system under test sees it.

A qualification run is invalid if the adapter's acceptance/classification disagrees with the independent oracle and that disagreement is not explicitly surfaced.

### 4.3 Fault-injection proof rule

For each failure-injection scenario, `injection_confirmed` is not a trusted assertion. It must be derived from independent observation appropriate to the fault class, for example:

- byte mutation: independent pre/post SHA-256 or byte-level evidence;
- size mutation: independent pre/post size;
- archive mutation: independent member listing/hash;
- process termination: independent process lifecycle evidence;
- provider failure: independent adapter event plus observed absence of expected acquisition output;
- cleanup failure: independent filesystem evidence showing the intended cleanup operation did not achieve its expected postcondition.

If the independent observer cannot prove the targeted fault occurred, the scenario is `BLOCKED`, not PASS.

## 5. Scenario specification

### FM-001 — Download failure cannot become VALID

**Setup:** valid requested date; acquisition boundary configured to fail.  
**Injection:** deterministic provider/download failure.  
**Expected:** no VALID record; no authoritative RAW presented as valid.  
**Forbidden:** VALID, or a later SKIP based solely on failed acquisition.  
**Recovery:** rerun with acquisition restored; successful acquisition may proceed normally.  
**Oracle:** manifest + filesystem + exit code.  
**Evidence:** failure injection confirmation, state snapshot, transcript, recovery result.

### FM-002 — Malformed tick content rejected

**Setup:** archive contains exactly one CSV with malformed rows/schema.  
**Injection:** malformed content delivered unchanged by the acquisition adapter.  
**Expected:** rejection; no VALID.  
**Forbidden:** promotion to VALID.  
**Recovery:** replace with deterministic valid fixture and rerun.  
**Oracle:** independent parser/classifier of fixture.  
**Evidence:** raw fixture hash, independent parser result, adapter delivery evidence, observed state, recovery result.

### FM-003 — Timestamp outside requested window rejected

**Setup:** otherwise valid ticks with at least one timestamp outside the requested date/window.  
**Injection:** out-of-window fixture delivered unchanged.  
**Expected:** rejection; no VALID.  
**Recovery:** corrected in-window fixture then rerun.  
**Oracle:** independently parsed timestamps compared to contract-declared bounds.  
**Evidence:** exact offending timestamp(s), bounds, fixture hash, observed state.

### FM-004 — Non-monotonic timestamps rejected

**Setup:** otherwise valid fixture containing a deliberate timestamp regression.  
**Injection:** non-monotonic fixture delivered unchanged.  
**Expected:** rejection; no VALID.  
**Recovery:** monotonic fixture then rerun.  
**Oracle:** independent timestamp ordering calculation.  
**Evidence:** first offending pair/index, fixture fingerprint, observed state.

### FM-005 — Invalid volume values rejected / zero policy respected

**Setup:** NaN, infinity, negative volume, and explicit zero-volume boundary fixtures.  
**Expected:** invalid values rejected; zero follows the frozen policy.  
**Recovery:** valid-volume fixture then rerun.  
**Oracle:** independent parser and numeric classification.  
**Evidence:** classification of each boundary value and observed state.

### FM-006 — Multiple CSV contents rejected as ambiguous

**Setup:** archive containing more than one CSV candidate.  
**Expected:** rejection; no VALID.  
**Recovery:** single-CSV archive then rerun.  
**Oracle:** independent archive enumeration.  
**Evidence:** member list and counts, observed state, recovery result.

### FM-007 — Post-copy corruption cannot poison restart

**Setup:** acquisition produces a valid candidate and reaches the post-copy validation boundary.  
**Injection:** mutate/corrupt the copied RAW before post-copy validation completes; separately test termination at the cleanup/quarantine boundary.  
**Expected:** failed acquisition; failed artifact removed/quarantined/ignored according to the frozen P-001 policy; no VALID.  
**Forbidden:** failed RAW remains authoritative or causes permanent restart BLOCKED merely because it exists.  
**Recovery:** fresh process starts from the exact observable post-failure state and verifies successful reacquisition is possible.  
**Oracle:** independent filesystem/hash inspection.  
**Evidence:** pre/post hash, mutation proof, termination proof where used, artifact disposition, manifest, recovery transcript.

### FM-008 — Post-VALID mutation cannot produce SKIP

**Setup:** establish a real VALID artifact and manifest proof.  
**Injection:** mutate RAW after VALID; test both changed-size and same-size content. If concurrency is in scope, synchronize a mutation during the SKIP authorization window.  
**Expected:** current integrity mismatch detected; SKIP forbidden.  
**Forbidden:** SKIP despite changed bytes.  
**Recovery:** restore exact original artifact; SKIP then becomes eligible only after identity match.  
**Oracle:** independent SHA-256/size.  
**Evidence:** before/after hashes, mutation record, manifest proof, concurrency/lock evidence if applicable, observed status, recovery status.

### FM-009 — Unchanged VALID artifact may SKIP deterministically

**Setup:** successful VALID acquisition.  
**Injection:** none; invoke repeatedly without artifact mutation.  
**Expected:** deterministic SKIP based on current integrity match.  
**Recovery:** repeated invocation must remain SKIP while artifact and proof remain unchanged.  
**Oracle:** independent hash/size and manifest parsing.  
**Evidence:** repeated state snapshots and equality proofs.

### FM-010 — Stale, inconsistent, or tampered manifest cannot authorize false state

**Setup:** valid/invalid combinations of manifest record and filesystem artifact.  
**Injection:** stale hash, wrong size, missing artifact, conflicting record, unrelated record, and **post-VALID manifest tampering** of hash/size/status fields.  
**Expected:** no false authorization of VALID/SKIP; manifest inconsistency remains observable.  
**Forbidden:** editing the manifest into agreement with a changed/corrupt RAW silently authorizes SKIP.  
**Recovery:** restore a coherent artifact/proof pair and verify expected behavior.  
**Oracle:** independent manifest parser plus independent filesystem identity and a separately retained expected-proof artifact where the contract requires it.

**Trust-boundary rule:** The manifest is not treated as an unconditionally trusted root of truth. If the implementation has no independent anchor for manifest provenance/integrity, the relevant claim remains bounded/TO-PROVE rather than being promoted to PASS.

### FM-011 — Concurrent manifest writers cannot silently corrupt evidence

**Setup:** two controlled processes targeting the same manifest under an explicitly declared concurrency model.  
**Injection:** synchronized concurrent writes.  
**Expected:** either serialized valid records or explicit failure; no silently malformed/interleaved evidence.  
**Oracle:** independent CSV/parser validation and record accounting.  
**Status:** **MANDATORY BLOCKER — TO-PROVE until runtime behavior is established.**

### FM-012 — Restart independent of hidden process state

**Setup:** execute each relevant scenario up to a defined lifecycle boundary, terminate process, then start a fresh process.  
**Expected:** second process derives state only from observable artifacts/manifest/configuration and behaves deterministically. Orphan RAW state must be handled according to P-001.  
**Oracle:** clean-process comparison and state snapshot.  
**Evidence:** PIDs/process boundaries, termination proof, state snapshots, repeated outcomes.

### FM-013 — Harness/oracle common-mode failure exposed

**Setup:** introduce deliberate disagreements between implementation and oracle assumptions using known adversarial fixtures, including at least one boundary-condition disagreement and one volume-policy disagreement.  
**Expected:** harness identifies the disagreement and refuses PASS rather than silently accepting implementation output.  
**Oracle:** independent fixture semantics and direct filesystem facts.  
**Status:** **CRITICAL MANDATORY BLOCKER — must PASS before any qualification PASS.**

### FM-014 — Static evidence cannot close runtime gates

**Setup:** record static code inspection separately from runtime scenario results.  
**Expected:** absent runtime evidence remains BLOCKED.  
**Forbidden:** converting static PASS into runtime PASS.  
**Oracle:** evidence ledger itself.  
**Status:** governance control.

### FM-015 — Semantic scope is not overclaimed

**Setup:** controlled fixtures whose provider/content identity cannot establish NAS100 semantic identity beyond the downloader's declared contract.  
**Expected:** downloader does not claim stronger semantic guarantees than contract supports.  
**Oracle:** provider documentation plus fixture metadata, independent of downloader parser.  
**Status:** **MANDATORY BOUNDED CONTROL.** It must be explicitly resolved as PASS-with-bounded-scope or remain BLOCKED/TO-PROVE; it cannot be silently treated as full semantic qualification.

### FM-016 — Cleanup failure cannot silently contaminate next run

**Setup:** force temp/quarantine cleanup failure.  
**Expected:** residual state is observable and cannot be mistaken for authoritative VALID/eligible SKIP; next invocation follows the deterministic orphan-state policy.  
**Oracle:** filesystem inventory and manifest state.  
**Recovery:** explicit cleanup/reinitialization followed by controlled rerun.

### FM-017 — Runtime environment incompatibility remains visible

**Setup:** execute under the exact supported PowerShell/runtime environment and at least one deliberately unsupported/mismatched environment if the contract specifies one.  
**Expected:** unsupported environment does not silently yield VALID; supported environment behavior is separately evidenced.  
**Oracle:** environment fingerprint + process result + state.  
**Status:** **MANDATORY BLOCKER — runtime qualification remains BLOCKED until executed and evidenced.**

## 6. Oracle independence requirements

The following are explicitly prohibited as sole critical oracles:

- calling the same `Test-TickFile` function used by the implementation;
- reusing the implementation's SHA-256 helper as the only integrity calculation;
- trusting the implementation's manifest lookup to prove its own manifest interpretation;
- inferring expected state from the implementation's printed status alone;
- declaring a test PASS because implementation and harness agree when both depend on the same unverified assumption;
- treating an injector's own `confirmed` flag as independent evidence;
- treating the acquisition adapter's fixture classification as independent evidence.

### Independence requirements

For every critical scenario, the harness must identify:

```text
SYSTEM UNDER TEST
OBSERVER
ORACLE
EVIDENCE SOURCE
ASSUMPTIONS
```

and must show that no critical oracle result is derived solely from the component under test or from an injector/adapter assertion.

### Mandatory independence self-test

Before qualification PASS, FM-013 must deliberately create a known disagreement between an implementation assumption and an oracle assumption. The harness must produce a non-PASS result and preserve evidence of the disagreement.

If this self-test cannot execute, **all critical runtime qualification remains BLOCKED**.

### 7.1 Mandatory evidence matrix

The verdict engine must use an explicit machine-checkable required-field set by scenario. At minimum:

| Scenario class | Additional mandatory evidence |
|---|---|
| Failure injection | `injection_id`, independent `injection_confirmed`, fixture identity, pre/post state |
| Integrity/SKIP | independent size + SHA-256, relevant VALID proof, mutation/recovery evidence where applicable |
| Post-copy recovery | process termination proof where injected, artifact disposition, fresh-process recovery evidence |
| Manifest scenarios | independent manifest parse, filesystem identity, record accounting |
| Concurrency | process identities/timing or lock evidence, concurrent outcomes, manifest integrity result |
| Oracle independence | explicit assumption set, disagreement injection result, independent oracle result |
| Environment | environment fingerprint, supported/unsupported classification, process result |

A scenario-specific manifest of mandatory fields must be generated by the harness specification/implementation and checked before verdict evaluation.

### 7.2 Evidence completeness rule

For every mandatory field:

```text
missing OR null OR unverifiable OR contradictory
    → NOT ELIGIBLE FOR PASS
    → BLOCKED unless executable evidence directly demonstrates a contract violation, in which case FAIL
```

A prose statement such as `injection_confirmed=true` without independent supporting evidence is insufficient.

The verdict engine must perform this completeness check **before** evaluating PASS conditions.

### 7.3 Evidence immutability

The evidence set used to establish a scenario verdict must itself be retained immutably or with a demonstrable append-only/versioned identity sufficient for later audit. The harness must not rewrite a failed evidence record into a PASS record.

## 8. Verdict algorithm

For each scenario:

```text
IF required execution cannot occur
    => BLOCKED
ELSE IF contract violation is directly demonstrated
    => FAIL
ELSE IF mandatory evidence schema is incomplete, null, contradictory,
        unverifiable, or lacks independent attribution
    => BLOCKED
ELSE IF scenario requires injection AND independent injection proof is absent
    => BLOCKED
ELSE IF critical scenario requires FM-013 independence proof
        AND FM-013 has not passed
    => BLOCKED
ELSE IF all mandatory evidence exists
        AND independent oracle agrees with expected state
        AND forbidden state is absent
        AND recovery requirement passes where applicable
        AND all scenario-specific acceptance predicates pass
    => PASS
ELSE
    => BLOCKED / TO-PROVE depending on whether execution or evidence is missing
```

A PASS is therefore a statement about the **tested scenario and current baseline**, not a universal proof of correctness.

### 8.1 Qualification promotion blockers

The following are mandatory blockers for promotion to runtime qualification and then to the Real Dukascopy gate:

- P-001 implemented and its FM-007/FM-012/FM-016 evidence passes;
- P-002 implemented and FM-008/FM-009 evidence passes;
- FM-013 passes its common-mode independence self-test;
- FM-011 passes or the concurrency model is explicitly bounded and the unsupported behavior cannot silently authorize success;
- FM-017 passes for the supported runtime environment;
- all critical failure-injection scenarios required by `SC-V33-001`, `SC-V33-005`, and `SC-V33-008` pass;
- no critical scenario is FAIL or BLOCKED;
- all mandatory evidence fields are complete and independently attributable;
- the implementation baseline is versioned.

No deferred scenario may be silently promoted to PASS merely because it is inconvenient or expensive to execute.

## 11. Promotion rule

This document does not promote V3.3 toward `QUALIFIED`.

The next promotion boundary is reached only after:

- V0.2 survives adversarial audit without untreated CRITICAL/HIGH architectural weakness;
- P-001 and P-002 are implemented;
- static review confirms the patch does not weaken any contract;
- the harness is executable on the target environment;
- the harness passes its own independence/self-audit checks;
- all mandatory regression and failure-injection scenarios execute;
- critical rejection and recovery scenarios produce reproducible evidence;
- no critical scenario remains FAIL or BLOCKED;
- mandatory medium/high controls are either evidenced or explicitly bounded by contract without silent overclaim;
- the resulting implementation baseline is versioned.

Only then may the project proceed to the real-data gate.
